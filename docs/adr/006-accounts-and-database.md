# ADR-006: Anonymous accounts and Postgres (M5)

- Status: Accepted (Vân approved the recovery code and Render's free Postgres on 2026-11-03)
- Date: 2026-11-03

## Context

Until M4 the app kept everything in the browser; a reload lost the mother's profile, check-ins and pinned notes.
M5 adds accounts and a database without collecting email or phone (CLAUDE.md, "Auth"). Open decision #1 (PIN
recovery) was answered: a one-time recovery code shown at sign-up.

## Decisions

- **Identity:** nickname (3-24 chars, unique ignoring case) + 6-digit PIN. PIN and recovery code are hashed with
  argon2id (`argon2-cffi`, library defaults), each with its own salt. Verification is constant-time; an unknown
  nickname still costs one dummy hash, and every login error is the same text, so nicknames cannot be enumerated.
- **Recovery code:** 16 characters from a 32-letter alphabet without `0/O/1/I` (80 bits), shown once as
  `XXXX-XXXX-XXXX-XXXX`; the mother must tick "I saved it" before continuing. A successful reset sets the new PIN,
  issues a NEW code, and signs out every other session. Trade-off: if she loses both PIN and code, the account
  cannot be recovered (no email to fall back on). This is stated on screen.
- **Sessions:** a 15-minute access token (signed JWT, HS256, `JWT_SECRET` from the environment) and a 30-day
  refresh token, both in `httpOnly`, `SameSite=Lax`, `Secure` cookies. Only a SHA-256 of the refresh token is
  stored. Refresh rotates the token; replaying a used one signs the account out everywhere (theft detection).
  One origin (API under `/api`, ADR-005) keeps the cookies first-party, so CSRF protection rests on `SameSite=Lax`
  plus JSON-only bodies.
- **Lockout:** per nickname (5th wrong try starts a lock) and per IP (20th), then 1, 2, 4... minutes up to 1 hour.
  Keys are counted whether or not the nickname exists. State is **in memory**: it resets on restart and is per
  instance. Acceptable for one instance and a handful of beta mothers; revisit before scaling out.
- **Stored per account:** profile + trusted contact, babies, check-ins (one per day), pinned notes. **Not stored:**
  chat messages (unchanged). Guests still store nothing on the server; what a guest entered is uploaded when they
  create an account, and an account that already has data wins over local guest data when they sign in.
- **Pinned notes and Tier 3:** `POST /notes` refuses a Tier 3 tier from the client AND any note whose text or
  topic matches the server-side safety keywords, so a modified client cannot pin crisis content (invariant 4).
- **Delete:** `DELETE /account` needs the PIN again and removes every row of the account.
- **Logs:** only event names and the pseudonymous user id; a test asserts nickname, PIN and codes never appear.
- **Schema:** SQLAlchemy 2 models, Alembic migration `0001`. A test fails if the migration and the models drift.
  The container runs `alembic upgrade head` before starting (skipped without `DATABASE_URL`, so guest-only runs
  still work); a failed migration stops the deploy and the previous version keeps serving.
- **Tests:** account tests run on in-memory SQLite locally and on a real Postgres service in CI
  (`TEST_DATABASE_URL`); the compose smoke test signs up, reads the profile and deletes the account against
  Postgres, and the post-deploy check does the same against the public URL.
- **Hosting:** Render free Postgres (`render.yaml`, Singapore, linked via `fromDatabase`). `JWT_SECRET` is
  generated by Render.

## Consequences

- **Render deletes a free database 30 days after it is created** (14-day grace to upgrade). Before then, upgrade
  the database or move to another free Postgres and restore a dump; otherwise accounts disappear. Calendar this.
- Render free Postgres has no backups beyond that; the beta is for 3-5 mothers who know this is a test.
- Existing Render service needs a Blueprint sync (dashboard) to create the database and the two new variables.
- Not done: memories and pin-to-memory extraction (M6), Tier 3 incident log (open decision #2), memory
  retention (#3), legal review of storing health data (#5; no compliance is claimed).
